# 검색 후 바로 쓰는 실용 콘텐츠·도구 아이디어

- 작성일: 2026-08-12
- 대상: 더샵 검단레이크파크 AB22·AB23 계약자·예비입주자와 가족
- 범위: 돈·권리·입주·하자·통근·아이·안전·생활·관리비
- 전제: Astro 정적 배포, 로그인·서버 DB 없음, 상세 입력은 브라우저 안에서만 처리
- 목표: 검색 결과를 읽고 닫는 페이지가 아니라 사용자가 **저장하고, 인쇄하고, 캘린더에 넣고, 현장에서 체크한 뒤 다시 가져오는 산출물**을 만든다.

## 1. 현재 제품에서 출발할 수 있는 것

현재 저장소에는 다음 기반이 이미 있다.

- 블록·타입·분양가 범위·납부 구조·중도금 일정·예상 입주일
- 계약금부터 입주비까지 계산하는 순수 계산 로직과 계산기 UI
- 입주 D-day 타임라인과 개발사업 상태·변경이력·출처
- 블록·타입을 브라우저에 저장하는 `profile.v1`
- 타입별 생활 해석과 동별 공식 유의사항

반대로 다음은 아직 없다.

- PDF·인쇄 전용 결과, ICS 캘린더, CSV·JSON 백업
- 사용자가 완료한 할 일, 현장 측정값, 하자 사진·재점검 기록
- 애플리케이션이 조회할 수 있는 동·층·라인별 가격 카탈로그와 AB22 유상옵션 구조체
- 확정 통학구역·단지 출입구 보행 실측·상가 실제 운영시간
- 2029년 이후 K-apt 관리비·입찰·계약 데이터

여기서 가격 카탈로그가 없다는 말은 **원천 공고에 가격표가 없다는 뜻이 아니다.** 제공 PDF 시각검수 기준 AB22 공고 7~8쪽에는 타입별 해당 동·라인과 `1/2/3~4/5~6/7~9/10~15/16~20/21층 이상` 구간의 공급금액·계약금·중도금·잔금 표가 있고, AB23 축약 공고 1쪽에도 타입별 층구간 가격표가 있다. 따라서 `동 선택→가능 타입 검증→층 숫자를 공고 구간에 매핑→공급가 조회`는 휴리스틱 없이 구현 가능성이 높다. 준비 과제는 원천 데이터 수집이 아니라 표 구조화와 원문 대조 테스트다.

따라서 아이디어의 `준비도`는 콘텐츠가 흥미로운지가 아니라 **현재 저장소 데이터로 거짓 정밀도 없이 만들 수 있는가**로 판정한다.

## 2. 공통 설계 규칙

1. 모든 도구에는 최소 하나의 행동 산출물을 둔다: `인쇄`, `PDF`, `ICS`, `CSV`, `JSON`, `현장 체크`, `완료 저장` 중 하나.
2. 서버가 없으므로 개인값은 기본적으로 메모리에 두고, 사용자가 명시적으로 저장할 때만 localStorage 또는 IndexedDB를 쓴다.
3. 개인 계약서·신분증·아이 이름·호수·사진을 서버로 올리게 하지 않는다. 백업 파일은 사용자가 직접 내려받고 보관한다.
4. 법률·세무·대출·하자 판정은 결론을 대신하지 않는다. 공식 근거, 확인 질문, 기한, 상담처로 연결한다.
5. 정적 사이트의 ‘실시간’은 금지한다. 시간표·영업·관리비는 기준일이 있는 스냅샷으로 표시한다.
6. 현재 기능의 단순 복제는 후보로 세지 않는다. 각 표의 `델타`에 새 행동이나 산출물을 명시한다.

### 평가 표기

- 준비도 `높음`: 기존 데이터·로직으로 바로 가능 / `중간`: 구조화·현장조사 1회 필요 / `낮음`: 입주 후 또는 외부 데이터 확보 필요
- 정적 적합성 `높음`: 브라우저 JS만으로 완결 / `중간`: 빌드 시 스냅샷·IndexedDB·카메라 등 추가 / `낮음`: 인증·중계 서버 없이는 핵심가치가 약함
- 위험 `낮음·중간·높음`: 개인정보, 법률·세무·의료 오해, 분쟁 가능성을 함께 평가

### 상위권에서 제외한 고득점성 아이디어

- `M2 금리 스트레스 시트`는 유용하지만 대출 가능액으로 오해할 위험이 커 M1 뒤 확장으로 둔다.

4. G5 공용계약·장기수선 확인 캘린더
5. L2 쓰레기·재활용 요일 포켓카드
6. L3 야간·휴일 생활 비상카드
7. L6 집 소모품 교체 캘린더
8. S2 정전·단수·승강기 멈춤 키트

입주 전에는 껍데기를 미리 만들지 않는다. K-apt 공개, 관리규약, 실제 배출일, 관리사무소 공식 연락처가 생긴 뒤 스냅샷과 기준일을 갖춰 연다.

## 6. 가장 작은 구현 순서 제안

제품 구현을 고를 때는 기능 수보다 공통 산출물 엔진을 먼저 본다.

1. **인쇄 스타일과 ICS 생성기**: M1·R1·I1·H5·K2·S6가 함께 사용한다.
2. **공고 고정 납부지시 모델**: M7이 블록·납부항목·예금주·공고 페이지를 한 레코드로 읽고, 계약서 재확인 전에는 완료 상태가 되지 않게 한다. 계좌번호는 단순 복사 버튼을 제공하지 않는다.
3. **로컬 체크 상태와 JSON 백업**: I1·I6·H1·H2·H5·L5가 함께 사용한다.
4. **현장 로그와 CSV 내보내기**: C1·C4·C5·C6·K3·S4가 함께 사용한다.
5. **로컬 사진 대장**: H2·H6·G1만 별도 IndexedDB 모듈로 격리한다.
6. **입주 후 공개데이터 스냅샷**: G3·G5·G6는 2029년 이후 별도 빌드 입력으로 시작한다.

첫 검증은 `M1 납부 캘린더 팩 + M7 납부계좌 잠금 카드 + H1 사전점검 체크팩` 세 가지가 좋다. 각각 납부계획, 송금사고 예방, 입주 현장이라는 큰 실패비용을 다루면서도 서버 없이 완결되고, 사용자가 실제로 파일을 만들거나 5요소 대조·체크를 끝냈는지 측정할 수 있다.

## 7. 구현 전 확인할 경계

- 현재 개인정보처리방침은 “동·호수를 묻지 않는다”고 밝힌다. 동·층 저장이 필요한 기능은 기존 약속을 바꾸기 전에 별도 제품 결정이 필요하다.
- AB22와 AB23은 1차 계약금·발코니·추가옵션의 지정계좌를 같은 계좌로 가정하면 안 된다. 중도금은 세대별 가상계좌이며 공고상 납부일·금액의 별도 통보를 기대하지 않고 공고·계약서·은행 안내를 스스로 대조하게 한다. 지정계좌 외 입금은 HUG 보증에서 제외될 수 있다는 공고상 주의를 결과 가까이에 둔다.
- 계산기 입력과 새 도구의 개인값을 분석 이벤트에 포함하지 않는다. 이벤트는 `export_ics`, `print_opened`, `checklist_completed` 같은 기능 완료 여부만 사용한다.
- 사진 기능은 저장공간 한도, EXIF·사람 얼굴·주소 노출 경고, 개별 삭제와 전체 삭제를 먼저 설계한다.
- 법률·세무·대출·하자·학교 화면에는 기준일, 공식 원문, 예외가 있을 수 있다는 문구, 최종 확인기관을 결과 가까이에 둔다.
- 정정공고·시간표·학구·관리비는 ‘마지막 확인일’을 숨기지 않는다. 오래된 스냅샷은 결과 대신 재확인 경고를 우선한다.
- 업체 견적표와 학교 방문표는 운영자 순위·추천·공개 리뷰로 확장하지 않는다.
