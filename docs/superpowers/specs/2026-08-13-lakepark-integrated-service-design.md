# 검단레이크파크 통합 서비스 설계

- 작성일: 2026-08-13
- 상태: 구현 전 승인 설계
- 대상 릴리스: 모바일 뉴스형 홈 + 비용 계산 + 입주 준비 + 단지 소식·생활 정보

## 1. 제품 한 줄 정의

검단레이크파크 계약자가 **우리 집 비용을 계산하고, 입주까지 할 일을 관리하고, 주변 사업의 현재 상태를 읽는** 정적 웹 서비스다.

모바일 앱처럼 기능 아이콘을 나열하지 않는다. 익숙한 모바일 뉴스의 읽기 흐름 안에 계산기와 체크리스트를 배치한다.

## 2. 확정한 결정

1. 기존 Astro 7 정적 사이트를 유지한다.
2. 스타일 기반을 Tailwind CSS 4 Vite 플러그인으로 교체한다.
3. React·Vue 같은 별도 UI 런타임은 추가하지 않는다. Astro 컴포넌트와 strict TypeScript 클라이언트 모듈을 사용한다.
4. 모바일 하단 앱 탭을 제거하고 반응형 상단 헤더와 가로 카테고리 메뉴를 사용한다.
5. Pretendard Variable을 기본 서체로 사용하고 안티앨리어싱과 숫자 고정폭 표시를 적용한다.
6. 메뉴와 버튼은 사용자의 행동을 그대로 말한다. 내부 용어인 `상태판`, `현실판`, `준비실`, `영수증`은 주요 메뉴에서 사용하지 않는다.
7. 공급가는 공고의 공식 가격표를 조회한다. 층 밴드 휴리스틱은 사용하지 않는다.
8. 공식 금액과 개인 조건에 따른 예상 비용을 시각적으로 분리한다.
9. 사용자 값은 서버로 전송하지 않는다. 선택 저장은 명시적 동의가 있을 때만 이 기기에 저장한다.
10. 시세 전망·투자 판단·가격 상승 예측은 제공하지 않는다.

## 3. 릴리스 범위

이번 `전체 구현`은 조사한 145개 아이디어를 모두 독립 기능으로 만드는 뜻이 아니다. 아래 세 작업공간을 완결된 하나의 릴리스로 제공한다.

### 3.1 비용 계산

- 동 → 실제 층 → 타입 선택
- 해당 동에 가능한 타입만 표시
- 공고 기준 공식 공급가 단일값·범위·불가 판정
- AB23 6304동 84A 1층·2층의 라인 가격 예외 처리
- 정확한 세대 존재 여부를 확인하지 못한 층의 계약서 확인 안내
- 계약금·중도금 6회·잔금 계산
- 발코니·구조화가 끝난 유상옵션 반영
- 취득세·등기비·중도금 이자·입주 준비비 예상 범위
- 계약 전·입주 시·입주 후 필요한 현금 구분
- 납부 일정 ICS 내려받기와 인쇄
- 블록·납부항목별 계좌 대조 카드
- 전매·거주의무·재당첨 제한 참고 시계
- 선택 동의 공고상 생활 영향 요약
- 기존 상세 계산 조건을 접힌 `계산 조건 바꾸기`에서 수정

### 3.2 입주 준비

- 입주예정월 통보, 사전방문 공지, 실제 입주가능일 통보, 선택 입주일, 입주지정기간 종료일을 사건으로 저장
- 사건 변경 시 관련 체크리스트와 ICS 재계산
- `다가오는 할 일` 중심의 입주 타임라인
- 사전점검 공간별 체크리스트
- 가구·가전 반입 실측표
- 이사·인테리어 견적 동일조건 비교표
- 하자 발견·접수·보수·재점검 로컬 대장
- 선택 사진의 IndexedDB 로컬 저장과 전체 삭제
- 입주일 열쇠·출입카드·계량기 인수 체크
- 전입·주소변경·학교 후속 체크
- 체크 상태 JSON 백업·복원, 인쇄, ICS 내려받기

### 3.3 단지 소식·생활 정보

- 기존 개발 상태 데이터를 모바일 뉴스 피드로 재구성
- 전체·교통·학교·공원·생활·행정 필터
- `운영 중`, `추진 중`, `계획`, `확인 필요` 상태 표시
- 마지막 확인일과 공식 출처를 기사 가까이에 표시
- `무엇이 바뀌었나`, `현재 어디까지 왔나`, `다음에 무엇을 확인하나` 세 문장 구조
- 2026년 운영정보를 2029년 사실로 단정하지 않는 재확인 시점
- 교통·학교·의료·안전·행정·폐기물·공원 생활 행동 카드
- 홈의 `오늘의 단지 소식`과 `최근 업데이트` 피드

## 4. 이번 릴리스에서 하지 않는 것

- 회원가입·로그인·클라우드 동기화
- 서버 데이터베이스나 사용자 사진 업로드
- 동·호수 기반 커뮤니티와 공개 하자 지도
- 실거래가·시세·목표가격·가격 상승 점수
- 업체 추천·순위·공개 리뷰
- 학교 배정 보장, 대출 승인 가능액 확정, 세무·법률 결론
- 실시간 버스·병원·상점 영업정보를 자체 수집하는 서버
- 푸시 알림과 이메일 자동 발송

### 5.3 카피 규칙

- 제목은 명사보다 질문 또는 행동으로 쓴다.
- 한 문장은 모바일 두 줄을 넘기지 않도록 짧게 쓴다.
- `확정`, `예상`, `확인 필요`를 금액과 날짜 바로 옆에 붙인다.
- `쉽게`, `안전하게`, `정확하게` 같은 추상적 약속보다 결과를 설명한다.
- 버튼은 `보기`, `계산하기`, `저장하기`, `달력에 추가`처럼 수행 결과가 드러나게 쓴다.

## 6. 시각 시스템

### 6.1 기본 방향

- 흰색 배경과 얇은 회색 구분선을 중심으로 한다.
- 카드가 아닌 기사 행을 기본 단위로 사용한다.
- 계산·경고·상태처럼 경계가 필요한 정보만 카드로 묶는다.
- 그라데이션, 유리효과, 큰 이모지, 두꺼운 앱 프레임을 사용하지 않는다.
- 모바일에서 본문 좌우 여백은 18px, 데스크톱 콘텐츠 최대 폭은 1180px로 한다.
- 데스크톱은 뉴스 본문과 빠른 계산기 또는 다음 행동 사이드바를 2열로 배치한다.
- 모바일은 뉴스 → 빠른 계산 → 최근 업데이트 순서의 단일 열이다.

### 6.2 타이포그래피

- 본문: Pretendard Variable 400~500
- 제목: Pretendard Variable 700~850
- 폴백: `-apple-system`, `BlinkMacSystemFont`, `Segoe UI`, `Apple SD Gothic Neo`, `Malgun Gothic`, `sans-serif`
- 렌더링: `-webkit-font-smoothing: antialiased`, `text-rendering: optimizeLegibility`
- 금액·날짜: `font-variant-numeric: tabular-nums`
- 본문 최소 16px, 입력·버튼 최소 16px, 보조정보 최소 12px
- 행간: 본문 1.65, 제목 1.25~1.35

### 6.3 색상

- 본문: `#191f28`
- 보조본문: `#6b7684`
- 구분선: `#e5e8eb`
- 주 행동: `#3182f6`
- 주 행동 배경: `#edf6ff`
- 운영·확정: 녹색 계열
- 추진·예상: 파랑 또는 주황 계열
- 확인 필요·위험: 빨강을 최소 면적으로 사용

다크 모드는 이번 릴리스의 필수 범위가 아니다. 운영체제 다크 모드 때문에 임의로 색이 바뀌지 않도록 밝은 테마로 고정한다.

## 7. 기술 아키텍처

### 7.1 프레임워크

- Astro 7, `output: 'static'`
- Tailwind CSS 4와 `@tailwindcss/vite`
- `src/styles/global.css`의 `@import 'tailwindcss'`
- Astro 레이아웃에서 전역 스타일 한 번만 import
- TypeScript strict 설정 유지
- Vitest 단위 테스트 유지

### 7.2 계층

```text
pages
  -> page sections / Astro components
  -> feature client controllers
  -> pure domain functions
  -> verified static data
  -> local persistence adapters
```

- `src/data`: 검증된 공식·편집 데이터만 둔다.
- `src/lib`: DOM과 프레임워크에 의존하지 않는 계산·판정·직렬화 함수만 둔다.
- `src/scripts`: 페이지 이벤트와 렌더링을 연결한다.
- `src/components`: 재사용 가능한 시각 단위만 둔다.
- 페이지 파일에 가격 판정이나 납부 계산식을 넣지 않는다.

### 7.3 기능 경계

| 모듈 | 책임 | 의존성 |
|---|---|---|
| `priceResolver` | 동·층·타입·라인으로 공식 공급가 판정 | 공식 가격 행·라인 배정 |
| `costEstimator` | 공급가에서 납부·세금·이자·입주비 계산 | 기존 `src/lib/calc` |

| `rightsClock` | 공고 기준 참고 기한과 재확인 상태 계산 | 공고 기준일·현행 규칙 |

## 8. 비용 계산 설계

### 8.1 공식 공급가 데이터

- 기본 가격 78행과 특별 가격 3행을 분리한다.
- 동·타입·라인 배정 115개를 별도 정규화한다.
- 금액은 원 단위 정수로 저장한다.
- 층 입력은 1~29 정수만 허용한다.
- 21층 이상은 공고상 21~29층 구간으로 제한한다.

```ts
type PriceInput = {
  block: 'AB22' | 'AB23';
  building: number;
  floor: number;
  unitType: UnitTypeCode;
  line?: number;
};

type PriceResolution =
  | { kind: 'exact'; amountWon: number; occupancy: 'confirmed' | 'needs-contract-check' }
  | { kind: 'range'; minWon: number; maxWon: number; candidateLines: readonly number[] }
  | { kind: 'unavailable'; reason: PriceUnavailableReason };
```

AB23 `6304동·84A·1층/2층`에서 라인이 없으면 범위를 반환한다. 라인을 선택하면 한 값을 반환한다. AB23 `6304동·84B·2층`은 2호 한 라인만 있으므로 585,500,000원 단일값이다.

### 8.2 빠른 계산 흐름

1. 동을 선택한다. 동 번호로 블록을 결정한다.
2. 해당 동의 가능한 층·타입 선택지만 활성화한다.
3. 공식 공급가를 조회한다.
4. 라인 예외일 때만 라인을 묻는다.
5. 공식 분양가와 납부 구조를 먼저 보여준다.
6. 기본 계산 조건으로 세금·이자·입주 준비비 범위를 보여준다.
7. 사용자가 원할 때 계산 조건을 펼쳐 바꾼다.

기본 계산 조건은 중도금 대출 60%, 연 4.5%, 이자후불, 일반 입주 준비, 가전 포함이다. 결과 바로 아래에 항상 노출한다.

### 8.3 결과 위계

1. 공식 분양가
2. 계약금·중도금·잔금
3. 입주까지 예상 총비용 범위
4. 시점별 필요한 현금
5. 대출로 넘겨받는 금액
6. 세금·이자·입주 준비비 세부
7. 우리 동 생활 영향
8. 계산 조건과 공식 출처

공식 분양가에 옵션·취득세·등기·이자·입주 준비비를 섞어 `확정 총비용`이라고 부르지 않는다.

### 8.4 계좌 대조

송금 전 완료 조건은 다음 다섯 가지다.

1. 블록 확인
2. 납부항목 확인
3. 예금주 확인
4. 공고 원문 페이지 확인
5. 은행·계좌번호를 공급계약서와 재확인

계좌번호만 복사하는 버튼은 제공하지 않는다. 송금 뒤 이체확인증 보관은 별도 단계로 둔다. 중도금은 세대별 가상계좌이므로 번호를 저장하지 않는다.

### 8.5 권리 시계

- 전매제한, 거주의무, 재당첨 제한을 서로 다른 카드로 표시한다.
- 공고 기준일과 현행 법령 기준의 `참고 시계`임을 명시한다.
- 실제 종료일 확정 또는 법률 가능·불가 판정을 하지 않는다.
- 기준일, 원문, 최종 확인기관을 결과에 붙인다.
- 기준이 바뀌거나 마지막 확인일이 만료되면 날짜 대신 `재확인 필요`를 우선 표시한다.

## 9. 입주 준비 설계

### 9.1 사건 기반 일정

고정 D-60·D-45를 확정일처럼 저장하지 않는다.

```ts
type MoveInEventDates = {
  expectedMonthNotice?: string;
  preVisitStart?: string;
  preVisitEnd?: string;
  confirmedMoveInStart?: string;
  selectedMoveInDate?: string;
  designatedPeriodEnd?: string;
};
```

날짜가 변경되면 기존 파생 할 일과 ICS를 새로 계산한다. 사용자가 이전 ICS를 삭제해야 한다는 안내도 함께 보여준다.

### 9.2 체크리스트

할 일은 카테고리보다 `지금`, `다음 30일`, `입주일`, `입주 후`를 우선한다. 각 항목은 다음 구조를 갖는다.

```ts
type MoveInTask = {
  id: string;
  phase: 'now' | 'before' | 'moveInDay' | 'after';
  title: string;
  action: string;
  dueDate?: string;
  sourceUrl?: string;
  recheckAt?: string;
  completedAt?: string;
};
```

학교·교통·의료·폐기물·공원은 2029년 재확인 시점을 갖는다. 현재 정보로 미래 이용 가능성을 보장하지 않는다.

### 9.3 하자대장

- 하자 ID, 공간, 관찰 내용, 중요도, 접수번호, 상태, 발견일, 방문일, 재점검 결과를 저장한다.
- 상태는 `발견`, `접수`, `방문 예정`, `보수 중`, `재점검`, `완료`다.
- 사진은 IndexedDB에만 저장한다.
- 사진 추가 전에 EXIF·얼굴·주소 노출 가능성을 안내한다.
- 개별 사진 삭제, 하자 건 삭제, 전체 데이터 삭제를 제공한다.
- 인쇄/PDF에는 사용자가 선택한 사진을 포함할 수 있다.
- JSON 백업은 하자 텍스트와 사진 식별자만 포함하며 이미지 바이너리는 포함하지 않는다. 사진은 별도 내려받기 안내를 제공한다.
- 모든 내보내기는 사용자가 직접 파일을 저장하는 동작이다.
- 법정 하자 여부를 자동 판정하지 않는다.

## 10. 단지 소식·생활 정보 설계

### 10.1 뉴스 카드

```ts
type EditorialUpdate = {
  id: string;
  category: 'transport' | 'education' | 'park' | 'life' | 'admin';
  headline: string;
  dek: string;
  status: 'operating' | 'inProgress' | 'planned' | 'recheck';
  changedAt?: string;
  checkedAt: string;
  whatChanged: string;
  currentMeaning: string;
  nextCheck: string;
  sources: readonly InfoSource[];
};
```

기존 `StatusItem`을 버리지 않고 파생 어댑터를 둔다. 상태·이력·출처 원장은 하나만 유지한다.

### 10.2 홈 편집 규칙

- 대표 기사 1개
- 빠른 비용 계산 카드 1개
- 최근 업데이트 3~5개
- 다음 입주 행동 1개
- 생활 정보 2~3개

대표 기사는 가장 최근 날짜만으로 고르지 않는다. 상태가 실제로 변했고 입주자 행동이 달라지는 항목을 우선한다.

### 10.3 상태 표현

- `운영 중`: 현재 실제 이용 가능 근거가 확인됨
- `추진 중`: 행정·계약·공사 단계가 진행 중
- `계획`: 목표 또는 계획이 있으나 실행 전
- `확인 필요`: 오래됐거나 미래 시점에 재확인이 필요

`확정`이라는 단어는 공식 금액·공고일처럼 변하지 않는 값에만 사용한다. 개발사업에는 `운영 중`, `추진 중`, `계획`을 사용한다.

## 11. 로컬 저장과 개인정보

### 11.1 저장소

| 데이터 | 기본 | 저장소 |
|---|---|---|
| 동·층·타입·계산 조건 | 세션만 | 명시적 동의 시 `profile.v2` |
| 입주 사건 날짜·체크 상태 | 이 기기에 저장 | localStorage |
| 견적표·하자 텍스트 | 이 기기에 저장 | localStorage |
| 하자 사진 | 사용자가 추가할 때만 | IndexedDB |
| 뉴스·생활 정보 | 빌드 데이터 | 정적 파일 |

### 11.2 프로필 마이그레이션

- `profile.v1`의 블록·타입·공급가·계약일은 검증 후 v2로 옮길 수 있다.
- v1에는 동·층이 없으므로 임의로 생성하지 않는다.
- v2 저장은 `이 기기에 내 선택 저장`을 사용자가 눌렀을 때만 한다.
- 파싱 실패·미지원 값은 저장하지 않은 상태로 강등한다.

### 11.3 공개 문구 변경

기존 `동·호수는 묻지 않습니다` 문구는 다음으로 바꾼다.

> 호수는 묻지 않습니다. 동·층·타입은 비용 조회에만 사용하며, 사용자가 선택한 경우에만 이 기기에 저장됩니다.

서버 전송 없음, 전체 삭제 위치, 사진 로컬 저장을 개인정보 처리방침과 각 기능 가까이에 함께 표시한다.

## 12. 오류와 결측 처리

| 상황 | 처리 |
|---|---|
| 동에 타입이 없음 | 선택지를 비활성화하고 `이 동에는 해당 타입이 없습니다` 표시 |
| 층 가격 행이 없음 | 결과를 계산하지 않고 공고상 공급 세대 없음 표시 |
| 층의 실제 세대 존재 미확인 | 가격은 표시하되 계약서 확인 배지 추가 |
| 라인별 가격이 다름 | 범위와 라인 선택 표시 |
| 옵션 가격 미구조화 | 0원으로 확정하지 않고 `별도 계약·미반영` 표시 |
| localStorage 사용 불가 | 현재 세션은 계속 동작하고 저장 불가 안내 |
| IndexedDB 사용 불가 | 사진 없이 텍스트 하자대장 제공 |
| 오래된 생활 정보 | 결과 대신 `이용 전 재확인`과 공식 링크 우선 표시 |
| 잘못된 가져오기 파일 | 기존 데이터를 건드리지 않고 오류 요약 표시 |

오류는 페이지 전체 예외로 처리하지 않는다. 실패한 기능만 낮은 단계로 동작하게 한다.

## 13. 접근성

- 모든 선택은 실제 `button`, `select`, `input`, `details`를 사용한다.
- 키보드만으로 선택·수정·내보내기가 가능해야 한다.
- 포커스 링을 제거하지 않는다.
- 상태는 색상만으로 구분하지 않고 텍스트를 함께 쓴다.
- 모든 입력에 연결된 `label`과 오류 메시지를 제공한다.
- 동적 결과는 `aria-live="polite"`로 알린다.
- 모션은 200ms 이하로 제한하고 `prefers-reduced-motion`을 따른다.
- 터치 대상은 최소 44×44px다.
- 본문과 배경 명암비는 WCAG AA를 충족한다.

## 15. 완료 조건

1. 모든 주요 페이지가 Tailwind 기반 공통 레이아웃을 사용한다.
2. 모바일 하단 앱 탭이 제거된다.
3. 홈이 뉴스형 피드와 빠른 계산을 제공한다.
4. 동·층·타입으로 공식 분양가가 판정된다.
5. 공식 가격 35개 테스트가 통과한다.
6. 공식 분양가와 예상 부대비용이 분리된다.
7. 납부 ICS·인쇄·계좌 대조·권리 참고 시계가 동작한다.
8. 입주 사건·체크리스트·견적·하자대장이 로컬에서 동작한다.
9. 단지 소식에 상태·마지막 확인일·다음 확인·공식 출처가 보인다.
10. 호수를 묻거나 사용자 입력을 서버로 전송하지 않는다.
11. 개인정보 처리방침이 실제 저장 동작과 일치한다.
12. 테스트·타입검사·정적 빌드가 모두 통과한다.

4. ICS·인쇄·계좌 대조·권리 시계
